# Skills del equipo SafePet

Cada carpeta contiene un `SKILL.md` (formato Agent Skills: frontmatter `name` + `description`). Los subagentes de `.claude/agents/` las cargan con el campo `skills:`; en Multica se suben/pegan por agente según la tabla.

| Skill | Agentes | Cuándo usarla |
|---|---|---|
| `technical-decision-facilitation` | charles-engineering-manager | Facilita una decisión técnica con varios especialistas: preguntas por rol, informes independientes, matriz de criterios ponderados y resolución de desacuerdos. Úsala al abrir o conducir un issue de decisión (p. ej. Architecture Decision Meeting). |
| `project-planning` | pepper-product-manager | Convierte una decisión aprobada en hoja de ruta y tareas pequeñas, ordenadas por dependencia, con alcance, exclusiones, criterios de aceptación y agente responsable. Úsala tras un ADR o al planificar un milestone. |
| `adr-writing` | charles-engineering-manager | Redacta y publica un Architecture Decision Record (ADR) en docs/adr con el formato y ciclo de estados del proyecto. Úsala cuando una decisión técnica deba quedar documentada. |
| `repository-audit` | vision-code-auditor | Audita un repositorio en modo solo lectura y produce un informe con evidencia: estructura, stack y versiones, comandos, pruebas, configuración y riesgos. Úsala antes de cualquier decisión de arquitectura o modernización. |
| `dependency-audit` | sage-research-engineer, vision-code-auditor | Inventaria dependencias .NET y npm con versión actual, última, estado de soporte y vulnerabilidades conocidas, sin modificar nada. Úsala en auditorías y antes de planificar actualizaciones. |
| `test-coverage-analysis` | vision-code-auditor | Analiza qué partes del código tienen pruebas y cuáles no, por capa y por riesgo, y propone dónde agregar pruebas primero. Úsala en auditorías o antes de refactorizar. |
| `architecture-decision-records` | tony-software-architect | Analiza alternativas de arquitectura y prepara el contenido técnico de un ADR: opciones realistas, trade-offs, matriz de criterios y consecuencias. Úsala cuando el Solution Architect deba proponer una arquitectura. |
| `system-design` | tony-software-architect, strange-cloud-architect | Diseña la estructura de un sistema: módulos y límites, flujos críticos, modelo de datos multi-tenant, integraciones y requisitos no funcionales. Úsala al definir o revisar la arquitectura de SafePet. |
| `api-contracts` | tony-software-architect | Define y revisa contratos de API REST: recursos, verbos, DTOs, errores, paginación, versionado, idempotencia y compatibilidad con el frontend. Úsala al diseñar endpoints o cambiar un contrato existente. |
| `backend-engineering` | bruce-backend-engineer | Guía para evaluar e implementar el backend C#/ASP.NET Core en capas de SafePet: capas, casos de uso, validación, autorización, concurrencia, errores y pruebas. Úsala al analizar o escribir código del backend. |
| `database-design` | reed-principal-engineer | Diseña y revisa el modelo de datos PostgreSQL/EF Core: entidades, claves, índices, multi-tenancy, integridad y migraciones seguras. Úsala al modelar tablas o revisar cambios de esquema. |
| `api-testing` | bruce-backend-engineer | Diseña y escribe pruebas de integración de la API ASP.NET Core con WebApplicationFactory y PostgreSQL real (Testcontainers), incluidas autorización por rol y aislamiento multi-tenant. Úsala al crear o modificar endpoints. |
| `frontend-architecture` | shuri-frontend-engineer | Evalúa y define la arquitectura de la SPA React: Vite, TypeScript, organización por feature, estado y datos remotos, routing por rol, formularios, rendimiento y DX. Úsala al analizar o estructurar el frontend. |
| `accessibility` | shuri-frontend-engineer, wanda-ux-ui-designer | Revisa y asegura accesibilidad WCAG 2.2 AA en la SPA (agenda pública, formularios, calendario, backoffice) con PrimeReact. Úsala al construir o revisar pantallas. |
| `frontend-testing` | shuri-frontend-engineer | Diseña y escribe pruebas del frontend con Vitest + Testing Library (y MSW para la API), priorizando flujos de usuario. Úsala al crear o modificar componentes y pantallas. |
| `ci-cd` | forge-devops-engineer | Diseña y revisa pipelines de CI/CD en GitHub Actions para backend .NET y frontend React: jobs por ruta, PostgreSQL de servicio, caché, checks requeridos y despliegue con aprobación manual. Úsala al crear o modificar workflows. |
| `containerization` | forge-devops-engineer | Crea y revisa Dockerfiles multi-stage para ASP.NET Core y docker-compose para desarrollo local con PostgreSQL. Úsala al contenerizar el backend o preparar el entorno local. |
| `cloud-cost-analysis` | strange-cloud-architect | Compara proveedores de hosting y base de datos (free tiers vigentes, límites, costos al escalar, lock-in) con fuentes y fecha de consulta. Úsala al decidir dónde desplegar backend, frontend y PostgreSQL. |
| `observability` | riri-performance-engineer | Define logs estructurados, health checks, métricas, trazas y alertas para el backend y frontend dentro de free tiers, sin exponer datos sensibles. Úsala al preparar el sistema para producción o diagnosticar. |
| `secure-coding` | natasha-security-engineer | Aplica prácticas de código seguro en el backend .NET y el frontend React de SafePet: autenticación, autorización, multi-tenancy, validación, manejo de errores y pagos. Úsala al escribir o revisar código sensible. |
| `owasp-review` | natasha-security-engineer | Revisa código, diseño o un diff contra OWASP Top 10 y OWASP API Security Top 10, con foco en fugas entre tenants y datos clínicos. Úsala para revisiones de seguridad de PRs o de arquitectura. |
| `secrets-management` | forge-devops-engineer, natasha-security-engineer | Detecta y previene secretos en el repositorio y define cómo gestionarlos (variables de entorno, user-secrets, gestores del proveedor, rotación). Úsala en revisiones, al configurar entornos o si aparece un secreto. |
| `test-strategy` | domino-qa-automation | Define la estrategia de pruebas de un cambio o proyecto: niveles, qué cubre cada uno, datos, entorno y criterios de salida, incluida la prueba de aislamiento multi-tenant. Úsala al planificar trabajo o revisar propuestas. |
| `regression-review` | domino-qa-automation | Revisa un cambio o propuesta buscando regresiones: comportamiento existente roto, contratos API/BD incompatibles, pruebas debilitadas y efectos en otros módulos. Úsala antes de aprobar un PR o una síntesis de decisión. |
| `acceptance-criteria` | pepper-product-manager, domino-qa-automation | Escribe y revisa criterios de aceptación verificables (dado/cuando/entonces) para issues de SafePet, detectando ambigüedad y casos borde. Úsala al crear issues o al revisar si una tarea está realmente terminada. |
| `scoped-implementation` | reed-principal-engineer, peter-junior-developer | Implementa estrictamente dentro del alcance de un issue aprobado: precondiciones, pasos pequeños, sin trabajo extra, PR con evidencia. Úsala siempre que vayas a escribir código para un issue. |
| `test-driven-development` | bruce-backend-engineer, peter-junior-developer | Aplica TDD (rojo → verde → refactor) en .NET y React para implementar comportamiento nuevo o corregir bugs con una prueba que falla primero. Úsala al implementar features o fixes. |
| `safe-refactoring` | reed-principal-engineer | Refactoriza código existente sin cambiar su comportamiento: pruebas de caracterización, pasos mecánicos pequeños, separación de refactor y cambio funcional, y rollback fácil. Úsala en modernización o limpieza de código. |
| `stitch-prompting` | wanda-ux-ui-designer | Redacta, ejecuta e itera prompts de Google Stitch para generar mockups de SafePet coherentes con el design system (móvil y escritorio), y revisa el resultado antes de exportar. Úsala al crear o actualizar pantallas en Stitch. |
| `design-system-tokens` | wanda-ux-ui-designer | Mantiene el design system de SafePet (docs/design/DESIGN.md) y su traducción a tokens de PrimeReact/PrimeFlex y FullCalendar. Úsala al crear o cambiar tokens, al revisar coherencia visual o al preparar el tema del frontend. |
| `design-handoff` | wanda-ux-ui-designer | Convierte mockups aprobados en una spec implementable (docs/design/<feature>/spec.md) y crea el issue para frontend-engineer con alcance, exclusiones, criterios y dependencias de API. Úsala cuando un diseño esté aprobado y deba pasar a implementación. |
| `agile-delivery` | pepper-product-manager, charles-engineering-manager | Opera Scrum + Kanban en Linear: planning, standup con despacho por capas (label `ready`), review/retro, DoR/DoD y WIP. |
| `technical-research` | sage-research-engineer | Investiga documentación, librerías y límites de servicios con fuentes fechadas, separando hechos de hipótesis. |
| `performance-engineering` | riri-performance-engineer | Mide y mejora rendimiento de BD, API y frontend con evidencia antes/después, solo en local. |
